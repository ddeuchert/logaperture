    Overhead¶

    What LogAperture adds to a log call, measured with JMH: with nothing configured, with rules, and with storm detection turned on.

    Measured on 2026-10-09, before 1.0

    These numbers are from the 1.0 code before beta 1, on one machine (the run). Everything an idle agent or a logger with message rules does is within its budget. Three checks are over, each with an open issue: see Over budget. The page is replaced by a new run when any of those are fixed.

    At a glance¶

    One INFO log call on one thread. Overhead is how much longer the call takes with LogAperture than without it, measured in the same run.

    What's installed Template message Concatenated message With a 20-frame exception
    Idle agent: nothing configured +13 % (+93 ns) +9 % (+67 ns) +13 % (+517 ns)
    20 drop rules on other loggers +8 % (+59 ns) +9 % (+67 ns) +12 % (+486 ns)
    20 rules on this logger, a trim matches +31 % (+218 ns) +35 % (+250 ns) −15 % (−604 ns)
    20 rules on this logger, a drop matches +56 % (+389 ns) +61 % (+443 ns) −73 % (−2,937 ns)
    Idle agent, storm detection turned on +18 % (+128 ns) +57 % (+413 ns) +13 % (+528 ns)

    How to read it:

    • Only calls that pass the logger's level check pay anything. A disabled DEBUG call never reaches LogAperture.
    • Template or concatenated. A template is the same String on every call: what JBoss Logging, message loggers and {0}/%s parameterized logging pass. Most WildFly logging is in the first column. A concatenated message ("order " + id + " failed") is a new string on every call. It costs about the same as a template, unless storm detection is on, which scans every message.
    • A negative number means the call took less time than with no agent: the matching rule dropped the record, or cut its stack trace, before it was written.
    • The baseline is about the cheapest real log call there is: JBoss LogManager, a short pattern formatter, output thrown away. About 0.7 µs, or 4 µs with the exception. Against a real file handler the same nanoseconds are a smaller share; see What a match saves.
    • The nanoseconds describe this machine only. It has a 2019 CPU, run without boost, so a newer one reports fewer. The percentages carry across hardware better.
    • Run to run, the idle agent moves by a few points. The same code measured +8.5 % on a template on 2026-10-07, and +13 % here: between JVMs, the JIT doesn't always compile the same way.
    • Storm detection is off unless you turn it on (--storm-detection=on, or logctl enable storms). See Log storms.

    What a match saves¶

    One INFO call through a real JBoss FileHandler (autoflush on), with 20 rules on the logger, the last of which matches, against no agent through the same handler. The exception has 100 frames.

    Matching rule Message Change vs no agent Per call
    drop template −52 % 1,079 ns vs 2,235 ns
    trim template +14 % 2,551 ns vs 2,235 ns
    drop exception −96 % 1,099 ns vs 24,515 ns
    trim exception −77 % 5,763 ns vs 24,515 ns

    A dropped record skips formatting and the write. A trimmed one is written with 5 frames instead of 100, which on a real handler saves far more than the rules cost. On a template message a trim has no stack trace to cut, so it only costs its rules.

    Several threads¶

    The idle agent at 1, 4 and 8 threads, each thread logging through its own logger:

    • Through one shared handler, the handler's own lock dominates and LogAperture adds nothing measurable: −3 % at 4 threads and −11 % at 8 on a template message, +2 % and 0 % on a concatenated one. The negative numbers are the lock's scheduling, not a speed-up.
    • Through a handler per thread, with no shared lock, the agent adds +6.5 %, +16 % and +25 % on a template at 1, 4 and 8 threads.

    The machine has 4 cores and 8 hardware threads, so the 8-thread runs share cores.

    What these numbers don't say¶

    JMH measures a hot loop in steady state: code and data in cache, and the JIT specialized on one call site. A real application's log path is colder, and its lock contention depends on its threading. Read these numbers as a lower bound for the fast path.

    Over budget¶

    Each part of the log path has a budget, fixed before measuring. Three are over:

    • A record a drop rule matches: +296 ns on a template against a 204 ns budget (#158). The record still goes through the cache that makes one event count once across handlers. A dropped record still costs far less than writing it.
    • Type-bound trim rules on a record with an exception: +538 ns for 20 rules against 204 ns (#177). Each rule walks the exception's class hierarchy.
    • Storm detection, when it is turned on: +364 ns on a concatenated message against 308 ns (#150). It is off by default.

    The first two are accepted for 1.0 as measured and scheduled for a 1.x release; the third is planned for 1.1.0.

    Details¶

    Where the idle agent's time goes¶

    Layer Template Concatenated Exception
    Rule filter, no rules −2 ± 16 ns +13 ± 18 ns +42 ± 37 ns
    Storm filter, installed but off +8 ± 11 ns +11 ± 21 ns +42 ± 40 ns
    trim support and top's byte counting +87 ± 12 ns +43 ± 18 ns +433 ± 89 ns

    Each row is the difference between two adjacent layers of the same run; rows near zero are within their own error. With an exception, most of top's share is encoding the whole record, trace included, to count its bytes.

    With storm detection turned on:

    Layer (storm detection on) Template Concatenated Exception
    Storm detection +93 ± 14 ns +364 ± 20 ns +79 ± 46 ns
    trim support −12 ± 11 ns +11 ± 22 ns +51 ± 57 ns
    top's byte counting +49 ± 12 ns +25 ± 21 ns +356 ± 70 ns

    1. The measured difference is under budget; the check fails on the upper end of an error bar that the 4 µs exception render widens. In each case one of the three JVMs ran about 100 ns slower than the other two: a JIT outcome, not a slower code path.

    Measure it yourself¶

    The benchmarks are in the source tree, and run on Linux, macOS or Windows. From a checkout:

    logaperture-bench/run-bench.sh --quick     # about 10 minutes, indicative only
logaperture-bench/run-bench.sh             # the full run, about an hour

    On Windows, powershell -ExecutionPolicy Bypass -File logaperture-bench\run-bench.ps1 -Quick. See logaperture-bench/README.md for what each scenario measures and how to read the report. For numbers you can compare with this page, run on a quiet machine with frequency boost off.
